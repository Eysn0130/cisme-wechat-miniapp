使用可用且授权的微信开发者工具和设备；需要本人扫码/设备交互时一次列出最少动作与测试订单范围。不得要求发送密钥/验证码。私有后台被工具站点策略拒绝时，不重复扫码当作解决方案，不代理/镜像/换工具绕过；仅使用政策允许且授权的官方读取通道，或请用户提供最少必要页面信息。没有权限/无法读取记为 unknown，不记为服务未开通。

分别核验：AppID/商户绑定与回调、微信合法域名及实际使用协议/路径、物流各项资格、域名ICP及腾讯云接入备案。无需通信的 socket 等不为凑四栏而额外开通；区分不适用和未知。Tencent 草稿、无根域A记录都不能证明缺少ICP备案。

用户提供的准确状态为“小程序备案 管局审核中”。保留来源与时间，不推断为代码版本审核中，不擅自撤回/重提。小程序备案、服务器域名备案、代码审核、微信发布是不同步骤；备案通过不会自动使未完成工程或未提审代码可公开运行。

## L. main 合并与不可变正式制品

PR22 的历史1057单元/804集成是旧HEAD证据；本轮新增提交使用新CI。完整审查源码差异、测试、依赖与未解决评审，不为赶 main 而绕过安全/原生证据。代码可合并与可以开启公开交易是独立门槛：经验证且门禁关闭的完整可回归代码可按仓库规则合并，但不得把仍有已知高风险缺陷的半成品标发布候选。

用户已要求 main 收口，满足审查条件后按实时合并规则将原PR或必要后续PR普通合并，校验 expected head 防竞态；不强推、不绕过保护、不修改安全规则。获取合并后 main 的准确完整SHA/tree及 push CI，核验实际 checkout；PR合成merge SHA、PR源HEAD、main合并SHA不能混写。

正式制品从这个已合并且验证过的 main 构建。核验原工程Node/lock、Linux x64依赖与原生库，生成不可变release manifest并执行增强后的 verify；打包后源码/关键配置变化需重新验证，不静默替换旧包。API/worker、管理端静态资源与原生小程序分别有明确制品/哈希与部署入口，现有后端打包脚本没有自动包含管理端，不能漏交管理员应用。

在最终main制品上做必要 staging回归再向production晋级，确保验证与上线是同一制品；若因main合并生成新SHA重建，重新绑定证据而非只改旧manifest字段。

## M. 真正的 production 升级，而非测试脚本改名

先审阅并实现基于既有保护数据的生产部署编排，接入目标 guard 和制品校验。严禁直接复用 `staging-candidate.py` 的“创建空验收库/本地object目录/过滤生产配置/切换staging服务”路径。

部署前列出：准确目标、当前与候选制品、真实service与EnvironmentFile、迁移清单/历史兼容性/可能锁表、生产DB与COS归属、备份与恢复验证、外部副作用门禁、管理入口、网络差异、切换和失败回滚步骤。实际配置与脚本默认不同则先修真实依据，不猜路径。

保留生产 `cisme` 数据及原 COS；不能用 staging数据库替换生产，不能调用 reset/seed/down 清空生产，不能从129空表恢复当作生产迁移。既有已执行SQL不得随意重写；检测历史版本/校验和差异，采用前向兼容扩展迁移及必要的数据校验。不可逆/破坏性迁移单独获取具体批准，并提供迁移与恢复证据。

在生产受保护范围内保存部署前数据库/必要全局权限/对象清单或版本恢复依据、配置与密钥恢复锚点，禁止将其上传GitHub。是否需要短写入窗口由真实业务和迁移决定；在本机正确端口进行非破坏性就绪验证，隔离候选worker避免重复消费/通知/资金请求。

按审查后的流程切换API/worker与管理资源，控制旧/新worker所有权和outbox，校验实际可见source SHA/tree/制品、正确DB/COS、真实HTTPS、管理员认证、业务门禁、错误与积压、告警到达、备份及恢复能力。服务能启动不是业务通过。

回滚必须考虑schema兼容与切换后的新写入：通常优先兼容旧应用回退/前向修复，不能盲目恢复切换前数据库导致新订单或资金事实丢失。不得宣称“零丢失/零停机”除非有实际设计与证据；异常时只回滚本次已批准范围，保留诊断不输出敏感内容。

## N. 备案等待期间的部署模式与最小人工项

最终必须明确报告是否已经部署到 `lhins-61ikz4mi`，不能拿 staging成功回答production完成。备案等待期间，在满足适用网络/备案条件和安全前置条件时可先完成生产制品安装与受限准备；公开交易、敏感外发和用户流量仍由真实审批/平台状态/验收门禁控制。已部署且关闭交易不等于可以卖货，但也不应因尚未公开发布而把已完成部署抹成“完全没做”。

上线前最小业务批准如真实退货地址/电话、有人受理的客服、政策版本/保留规则缺失，整理成一份明确表单，只要求真实不可推断值与一次批准。实现相应代码、配置校验和staging合成验收不应等这些值才开始。严禁为了把 releaseReady改true而填写占位联系方式或伪造批准。

用户本轮未要求自动付费续费，未授权真实资金或微信正式提审/发布。其余已授权的安全可逆准备持续推进；必须等待的外部动作说明精确阻断项、已完成替代验证和下一动作，不反复把技术缺口推回用户。平台备案完成后仍核验最终代码审核、版本/域名/隐私/支付状态，再在获得对应批准时提审与发布。

# PR22 商品图保全与当前小程序证据边界（2026-09-25 PDT）

## 来源与产品裁决

- 以 PRD V2.1 R4 的 P20「设置与协议」、§11.3 隐私要求及 R4-A 商品目录的真实业务状态为准。用户截图里的 `local-acceptance-v1` 和 `.invalid` 地址是旧隔离验收数据，不是用户要求的产品文案。`mobile-ui-ux-designer` 用于确认申请、反馈和记录顺序，`design-taste-frontend` 仅辅助版式和文字层级；实现仍为微信原生页面。
- 旧隐私页曾把 `/v1/legal` 的版本、主体和联系字段直接放在申请表上方，因而暴露夹具值。修正提交 `352c842` 之后，该页是“个人信息申请 → 申请事项与说明 → 提交申请 → 申请进度”，人工协助只进入已有客服申请页。当前源码没有 `local@example.invalid`，也不在隐私申请页展示法律接口的原始版本。旧画面的出处、缺陷和原生交互范围保存在 `docs/evidence/visual/review-r18-pr22-current-5fcaa41d-20260925/UX-REVIEW.md`；`r24-community-fixture-da564b98-20260925` 是之后但仍早于本轮商品页改动的历史 40 路默认帧。
- 已发布的历史协议 JSON 仍有未经证实的微信“反馈”联系说法。2026-09-23 法律候选正文只写现有微信小程序客服；新版未发布。无法登录时能否进入同一客服，以及正式微信环境的真实送达，仍需验证；不能把“反馈”当作已经确认的客服渠道，也不能自行增加邮箱、电话或另一套客服。

## 新发现的问题与修正

- 退役图片迁移 95 已在前一阶段收窄到三条精确历史预览种子，并保留未被批准删除的管理员商品图。进一步检查发现：商品编辑页即使只改名称，也会将未显示的原图路径替换为品牌占位图并随 `PUT` 提交，造成旧图记录被覆盖。
- 已有商品的原生编辑请求现在省略 `imagePath`；新建商品仍提交允许的品牌图标。服务端把“省略图片字段”解释为保留锁定行的现有 `image_path`，显式传入 `null` 或已批准图片仍按原契约处理。事务与版本冲突检查不变。
- 管理页使用品牌图标作安全预览时，明确提示“原商品图记录已保留；此处仅显示品牌图标。保存资料不会替换原图。”，避免把占位预览误说成原图。提示字号提高到 24rpx。此文案只表示数据库中有原图记录，不承诺旧文件已获展示授权或对象仍可下载。

审阅基线：`a3a2d5bf9ea1735b0fd324d19e4bd2c00e794fc4`，原 PR22 / `codex/fulfillment-lifecycle-20260922`。

## 已定位的源码问题

1. `http.ts` 原先把原生合法域名、DNS、TLS、拒绝连接等失败合并为 NETWORK_ERROR；账号页又把 HTTP/响应结构异常合并为 unreachable。仅凭页面文案不能定位备案、哪台服务器或微信身份问题。
2. 账号页对 `/v1/legal` 仅做 TypeScript 类型声明，没有运行时验证。隔离 A/B 已复现：`ready:"false"` 和重复活动协议版本在旧实现中可被当作就绪；HTML 成功响应则被错误归为网络失败。这不是生产出现过上述响应的证明。
3. 现有 DevTools / miniprogram-ci 预览入口检查声明和静态结构，但不实际读取目标协议接口，因而可能生成无法登录的普通二维码。
4. 协议未就绪时整个同意行被降低不透明度，连失败解释和查看协议入口也被一并淡化；数字“1”的重复登录说明占用了首屏空间。

## 本次修改

- 严格验证就绪布尔值、必需版本、重复活动版本；不放开同意，不使用假协议或开发身份替代正式登录。
- 保留取消、超时等旧语义；可识别的原生错误分别投影到固定诊断码。
- 账号页保存 `legalFailureCode`，不保存/输出原始 errMsg、响应正文、鉴权头、令牌或微信 code；版本刷新和异步交错保护保留。
- 删除重复数字步骤行，恢复协议失败说明的可读性；保留手机号可选、访客路径、历史隐私办理和原生授权按钮。
- 复用现有发布脚本：`npx tsx scripts/wechat-release.ts diagnose` 对配置中的预发与正式 API 各做一次匿名 GET；无需提供新凭据。
- 标准非本地预检/二维码生成及现有 miniprogram-ci 入口增加同一有界读取检查：不跟随重定向，不禁用 TLS 校验，最多读取 1 MiB，全请求预算默认 8 秒。成功只证明该执行机器读到合格协议元数据，不能证明微信合法域名、手机、AppID/密钥匹配或生产运营态已经通过。
- 未改变 API 域名映射、云服务模式、备案状态、评审规则、支付权限或生产配置；没有新增第二管理后台、产品功能或依赖。

# CISME 自主注册与云端交付核验

## 结论

CISME 的消费者注册不应设置“内部体验登记”条件。公开内容可直接浏览；会员通过首页「会员账号」进入，阅读并确认正式协议后完成微信身份建档，手机号作为独立授权步骤按需绑定。微信体验版的体验成员名单属于平台分发限制，与上架后消费者的业务注册条件不同。本次原生代码已按此边界调整，但正式协议、真实用户授权和体验版真机验收尚未闭环，不能据此宣称已可正式发布。

社区保留「精选」「推荐」「关注」；只有业务系统中获得团队角色的真实会员才看到「审核」。微信开发者工具的开发者身份不直接赋予业务审核权限。推荐归因沿用 PRD 的首次有效邀请关系，后续购货归因与返佣应按交易与财务规则另行实施，不能把会员编号直接解释为佣金账户。[1]

## 注册与身份

PRD §5.1 要求以 AppID 和 OpenID 唯一标识微信身份，并以幂等方式建立会员、积分账户和来源记录。缺失已验证 UnionID 时不得猜测合并；手机号重复也不得自动将两个会员的数据合并。公开浏览不能强制手机号授权，营销订阅与其他可选许可独立选择。注册、绑手机和完善资料均不发 R0 积分。[1]

账号页现从 `/v1/legal` 读取两份生效文件，协议未就绪时禁止提交注册。服务端在建档事务中再次校验同意的版本；因此修改客户端状态不能跳过真实协议版本检查。协议阅读页支持正文、版本和重试，发布脚本要求用户协议与隐私政策成对发布，并拒绝覆盖既有版本的不同正文。

手机号接口接收微信一次性授权 code，服务端向微信交换手机号；核对返回 AppID，按会员 ID 作为附加认证数据进行 AES-256-GCM 加密，使用独立 HMAC 密钥建立盲索引。返回值与审计只含脱敏信息。重复 code 对同会员幂等，对其他会员拒绝；已关联其他会员的号码进入核验流程，不自动合并。该实现的集成测试使用明确的模拟微信响应，不等价于真实手机授权验收。

两枚独立手机号密钥及版本已保存到云端 cismeApi 配置，原有凭据没有写入源码。正式协议库目前无生效正文，因此即便加密配置就绪，真实注册仍不能通过。缺失的运营主体、联系渠道及正式文本不能由示例内容替代。微信接口能力是否对该小程序实际开通，也必须以真实授权结果确认，不能只凭代码或密钥齐备推断。

## 社区与团队权限

「精选」默认展示品牌内容，「推荐」展示已发布的用户内容，「关注」由服务端按已关注作者筛选后分页；避免客户端仅过滤首批推荐数据而漏掉已关注作者。关注关系保存到数据库，用户内容须通过既有审核、发布许可和上线开关。

「审核」页面复用服务端角色校验和复核分工，支持审核及发布队列。授权脚本仅接受已建立真实微信身份的会员，并记录授权审计。由于真实云端会员尚未形成，首批管理员和开发者尚未绑定；完整会员编号现可在「我的」复制，文案已改为会员编号，避免将其误作入场资格。

当前实现并不说明全部审核状态已在真机验证。尤其媒体展示、拒绝与重试、四眼复核、撤销许可后的内容隐藏，仍需在正式体验环境由独立真实账号验收。自动化测试覆盖权限与事务边界，但不替代这种验收。

## 上传通道

云函数同步请求存在请求体限制，Base64 编码还会扩大载荷，不能把 10 MiB 文件整体塞入一次调用。[2] 本次采用最多 20 个、每个不超过 512 KiB 的 JSON 分片，再由服务端组装并交给现有对象存储流程。分片与父上传凭证、顺序、过期时间和媒体状态共同校验；完成或清理时移除中间数据。

本地集成测试覆盖 10 MiB 边界及重复、失序等约束。原生开发者工具中，512 KiB 测试载荷经 `wx.cloud.callHTTPFunction` 到达真实云端，收到预期的 `UPLOAD_UNAVAILABLE`，因为测试使用不存在的媒体 ID。这证明该体积的传输与路由可达，不证明完整业务上传成功；没有为这次探测创建伪造会员或媒体记录。

预览和体验运行时现指向 cismeApi；正式 release 目标仍未配置。云端和本地会话按目标分别存储，禁止本地模拟身份令牌混入云端会话。发布预检现识别云函数目标，但仍要求该通道的证据，保留隐私、协议及当前源码验收检查。

## 后台执行与安全

HTTP API 不运行常驻后台循环。独立普通函数 cismeWorker 已部署，单次执行复用既有发布及清理事务，并释放连接。函数级安全规则禁止客户端调用；管理端与定时器不受该客户端规则限制，因此函数入口另要求独立密钥。[3]

官方定时触发器支持七字段 Cron，事件中 `Message` 是字符串，管理接口可通过 `CustomArgument` 配置传入内容。[4][5] SCF 原生接口支持该参数，但实际查阅官方 `@cloudbase/manager-node` 5.8.6 的 `createFunctionTriggers` 实现，CloudBase 常规配置只转发 name/type/config，不能假设自定义 Message 会保存。入口因此另支持由独立密钥生成的不可预测定时器名称，并验证 Type 和名称；单独伪造 Type 不足以通过校验。云端无密钥调用已返回 `WORKER_TRIGGER_UNAUTHORIZED`；带密钥的完整执行在 512 MB 配置下于约 8 秒完成，返回 completed:true。每分钟定时器已保存；12:47 和 12:48 两次自动触发均记录 200 调用成功，耗时分别为 8013 ms 和 7310 ms。

同一 Worker 源码连接真实数据库与对象存储的一次本地执行返回 `published: 0, cleaned: 0`。这个结果只证明执行路径可连接及完成，不能替代云端冷启动、超时和实际定时触发证据。现已开启云函数日志，仅采集启用之后的新调用。

## 推荐归因与后续商品返佣

PRD §8.3 默认归因窗口为首次有效访问后 30 天，首次有效邀请关系不覆盖，自然复购在无有效窗口时不归因。成交展示记录 first/last touch，成交积分默认末次有效触点且同订单只奖励一人；退款按有效支付金额重算。[1]

本次加强访问归属、过期及撤销检查，保留已有自我邀请拒绝与幂等控制。消费者无需拿推荐码换取注册资格。后续商品订单、支付、退款、佣金结算、对账及规则版本需要作为完整交易系统交付；当前 R0 范围不应展示未经实现的现金返佣承诺。

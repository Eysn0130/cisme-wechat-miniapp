# ADR 0011 — Commercial membership, formal UGC and money gates

Status: accepted for incremental development; public UGC and real funds **not approved**. 2026-09-12. PRD authority: `CISME-产品需求文档-PRD-V2.1-R4.md` §6.8 (R4.2 construction revision), §6.6.2 and §7. This ADR does not supersede the privacy or release gates in ADR 0002/0009.

## Decision register

| Question | Engineering default used in isolated tests | Formal approval still required |
|---|---|---|
| Commercial qualification | An authorized operator grants a time-limited qualification; an account row is never automatically a commission member | Eligibility, benefits, duration, suspension and appeals |
| Referral attribution | The buyer explicitly confirms one direct relation; ordinary clicks and legacy `share_attribution` cannot establish cash rights | Attribution lifetime, repeat purchases, existing users, merges and disputes |
| Rate | 2000 bps global default; member override 2000–3500 bps; second person decides a proposal | Effective-time policy, exceptions, authority and approved rate schedule |
| Order snapshot | Direct referrer, rule, rate and cash merchandise are frozen with the order | Applicability to renewals, promotions and qualification transitions |
| Commission basis | Integer cents, merchandise cash after allocated discounts and points tender, excluding freight; cumulative refund target with half-up rounding at order total | Allocations, rounding, tax, qualifying SKUs, refunds and chargebacks |
| Availability and settlement | Verified payment starts pending; release needs approved fulfilment/after-sales facts; merchant transfer success and reconciliation alone mark paid | Release window, recipient identity, transfer scenario, tax, recovery, reconciliation and payout cadence |

## Source of truth and permissions

`member` remains the account. `commercial_membership`, stable `commercial_referral_code`, immutable `commercial_referral_relation`, `commission_rate_rule` and `commission_order_snapshot` are separate facts. Cash `commission_ledger_entry` remains separate from points. `member.profile.read` allows the minimum member list/detail, while `member.manage` grants or suspends qualification. `commission.rate.manage` proposes a rule, and `commission.rate.approve` must be held by a different person. `commission.read` is required for referral details and rate; `commerce.order.read` is additionally required for order details. Neither commercial qualification nor client-side UI state is a management capability. Public profile data comes from the existing approved allowlist.

Qualification, referral confirmation/code and rate mutations are deliberately rejected in staging and production until the commercial rules receive separate approval. A development qualification cannot be mistaken for a production entitlement. Member list counts and status labels exclude blocked, deleted and expired qualifications; changing accounts clears private management views before reloading.

Normal users can create formal UGC without an invitation. A post has a current working revision and a separate published revision; editing cannot replace public content until a new revision passes review and independent publication. An original upload remains private. The scanner uses a 45-minute signed source URL and records its text/image fact by post revision or image SHA-256. WeChat v2 results `pass`, `review`, `risky` and errors are distinct; only `pass` can reach a human approval, and the human approval does not enable a public post by itself. Callback signatures, trace IDs and app ID are checked; inbox replay is idempotent. Late callbacks cannot make a deleted or superseded revision public. Approved public images are rotated, resized and encoded as WebP derivatives without original metadata.

An editor can recover locally cached unsaved fields after an interrupted session when the server draft version and session still match. Private image previews use short-lived, owner-scoped URLs. Moderators cannot request a private unsubmitted draft by direct ID. Later risky scan results take precedence over an earlier safe callback, while the scanner does not overwrite a conclusive result by starting another scan. The gateway serializes upload writes against completion, and reusable direct S3 form uploads are disabled for formal UGC. A removed account or post cannot continue appearing through the public detail/media endpoints.

The formal feed has a separate followed-author query. A signed-in user can add or remove an author from a public post; the server rejects self-follow, blocked relationships and inactive authors. Blocking removes the follow in the same transaction. The native community uses a distinct following tab and an honest empty state. A public author page uses only the approved display-name/avatar allowlist and published posts; its native states remain unverified. Messaging and a formal appeal case path still need implementation and review.

`UGC_GO_LIVE_GATE`, the emergency switch and an expiring signed approval are all required for public service. Production/staging configuration additionally needs the WeChat app secret, callback token, fixed HTTPS scan origin and background worker. The callback currently accepts WeChat's signed plaintext JSON mode; encrypted message mode and the real callback configuration must be tested before approval. Scanner failure leaves content pending. Comment text is scanned separately before human approval; nickname changes still need an equivalent live text-safety integration and remain a release gap.

## Funds boundary

The existing checkout creates only `pending_payment` synthetic orders and may cancel or expire them. It records a reproducible direct-referrer/rate snapshot, but does not accrue commission. `paymentAvailable=false`, `implementedTransactionProfiles` is empty and there is no real payout endpoint. The WeChat Pay v3 protocol adapter verifies platform signatures over raw bytes, decrypts AEAD resources, checks merchant/AppID/order/amount/currency/payer identity and queries an unknown result with the original merchant order number. A separate internal inbox persists a verified payment notification before acknowledgement. Its worker locks the order, rejects synthetic sources, terminal orders, payments outside the order window, inconsistent merchandise lines or an inflated commission basis, consumes reserved stock, records a paid transition and accrues exactly once from a verified-commerce snapshot. Synthetic pending orders may expire; future verified-commerce orders must reconcile an unknown payment state before expiry. The result can be rebuilt from append-only facts. An isolated signed synthetic protocol fixture covers replay, cancellation conflict and inflated-basis rejection. The inbox is not mounted as a payment callback route and no current checkout can create a `verified_commerce` order; these tests are not live payment evidence.

An additional internal refund inbox now verifies signed and decrypted WeChat refund notifications against a **previously stored** merchant refund number, applied payment, original transaction, order and cash amounts. Its worker validates line-level cash allocation and cumulative refunded amounts, then appends a reversal toward the order-level rounded commission target. Two partial refunds, replay, abnormal-to-success and overdraw are isolated fixtures. The intent table does not create a refund request at WeChat, and no refund callback route is mounted. The current order model does not support voucher refunds; those facts become exceptions rather than guesses. The applicable discount, points, qualifying-SKU and refund allocation policy still needs approval and an authoritative command path.

The next required money slice is real refund application/query compensation, fulfilment and after-sales release, atomic payout reservation, final transfer confirmation and reconciliation. The pure calculation policy also covers discount allocation and a bucket projection; those functions have no live settlement authority. A transfer acceptance, pending user confirmation or unknown result must remain processing; unknown result requires querying the same merchant order number. Available and settled balances remain zero until approved, verifiable facts and the missing workflows exist.

## Deployment sequence and evidence

Forward migrations `202609120002`–`202609120008` were exercised only in isolated local test databases. Production migration, storage permission changes, public UGC, real payment, refund and transfer remain outside this authorization. Before either public gate can open: complete protocol wiring and reconciliation, review merchant/WeChat permissions and applicable terms, obtain named financial/content governance approvals, migrate staging, test callback and retries with real platform credentials, run native WeChat Developer Tools and iOS/Android acceptance against the exact source package hash, then request separate production authorization.

# ADR 0011 — Commercial membership, formal UGC and money gates

Status: accepted for incremental development; public UGC and real funds **not approved**. 2026-09-12. PRD authority: `CISME-产品需求文档-PRD-V2.1-R4.md` §6.8 (R4.2 construction revision), §6.6.2 and §7. This ADR does not supersede the privacy or release gates in ADR 0002/0009.

## Decision register

| Question | Engineering default used in isolated tests | Formal approval still required |
|---|---|---|
| Commercial qualification | An authorized operator grants a time-limited qualification; an account row is never automatically a commission member | Eligibility, benefits, duration, suspension and appeals |
| Referral attribution | The buyer explicitly confirms one direct relation; ordinary clicks and legacy `share_attribution` cannot establish cash rights | Attribution lifetime, repeat purchases, existing users, merges and disputes |
| Rate | 2000 bps global default; member override 2000–3500 bps; second person decides a proposal | Effective-time policy, exceptions, authority and approved rate schedule |
| Order snapshot | Direct referrer, rule, rate and cash merchandise are frozen with the order | Applicability to renewals, promotions and qualification transitions |
| Commission basis | Integer cents, merchandise cash after allocated discounts and points tender, excluding freight; cumulative refund target with half-up rounding at order total | Allocations, rounding, tax, qualifying SKUs, refunds and chargebacks |
| Availability and settlement | Verified payment starts pending; release needs approved fulfilment/after-sales facts; merchant transfer success and reconciliation alone mark paid | Release window, recipient identity, transfer scenario, tax, recovery, reconciliation and payout cadence |

## Source of truth and permissions

`member` remains the account. `commercial_membership`, stable `commercial_referral_code`, immutable `commercial_referral_relation`, `commission_rate_rule` and `commission_order_snapshot` are separate facts. Cash `commission_ledger_entry` remains separate from points. `member.profile.read` allows the minimum member list/detail, while `member.manage` grants or suspends qualification. `commission.rate.manage` proposes a rule, and `commission.rate.approve` must be held by a different person. `commission.read` is required for referral details and rate; `commerce.order.read` is additionally required for order details. Neither commercial qualification nor client-side UI state is a management capability. Public profile data comes from the existing approved allowlist.

Qualification, referral confirmation/code and rate mutations remain restricted to the isolated engineering profile. A development qualification cannot be mistaken for a production entitlement. This environment check is **not a final approved-rule implementation**: an approved, versioned commercial policy with a named owner, effective interval, applicable environment and independent approval is still needed before formal qualification can operate. Member list counts and status labels exclude blocked, deleted and expired qualifications; changing accounts clears private management views before reloading.

Normal users can create formal UGC without an invitation. A post has a current working revision and a separate published revision; editing cannot replace public content until a new revision passes review and independent publication. An original upload remains private. The scanner uses a 45-minute signed source URL and records its text/image fact by post revision or image SHA-256. WeChat v2 results `pass`, `review`, `risky` and errors are distinct; only `pass` can reach a human approval, and the human approval does not enable a public post by itself. Callback signatures, trace IDs and app ID are checked; inbox replay is idempotent. Late callbacks cannot make a deleted or superseded revision public. Approved public images are rotated, resized and encoded as WebP derivatives without original metadata.

An editor can recover locally cached unsaved fields after an interrupted session when the server draft version and account still match. Local text, declaration and media-ID backups are pruned after seven days on launch/foreground/editor use and cleared on logout or session switch; no bearer token is stored in the backup. Private image previews use short-lived, owner-scoped URLs. Moderators cannot request a private unsubmitted draft by direct ID. Later risky scan results take precedence over an earlier safe callback, and comment approval consults the latest scan. The scanner does not overwrite a conclusive result by starting another scan. The gateway serializes upload writes against completion, and reusable direct S3 form uploads are disabled for formal UGC. A removed account or post cannot continue appearing through the public detail/media endpoints.

The formal feed has a separate followed-author query. A signed-in user can add or remove an author from a public post; the server rejects self-follow, blocked relationships and inactive authors. Blocking removes the follow in the same transaction. The native community uses a distinct following tab and an honest empty state. A public author page uses only the approved display-name/avatar allowlist and published posts. Comment, reaction, collection, report and appeal paths enforce account and block boundaries. A report snapshots the revision seen by the reporter; the queue shows that revision, and a changed published revision cannot be hidden through a stale report. A moderator cannot adjudicate or read queue detail for a report on their own content, nor an appeal they handled or reported. Governance policy and all native states still need review. Messaging remains outside this slice.

`UGC_GO_LIVE_GATE`, the emergency switch and an expiring signed approval are all required for public service. Production/staging configuration additionally needs the WeChat app secret, callback token, fixed HTTPS scan origin and background worker. The callback currently accepts WeChat's signed plaintext JSON mode; encrypted message mode and the real callback configuration must be tested before approval. Scanner failure leaves content pending. Comment text is scanned separately before human approval; nickname changes still need an equivalent live text-safety integration and remain a release gap.

## Funds boundary

The ordinary checkout still creates synthetic `pending_payment` orders and does not accrue cash commission. A separate `APP_ENV=test` profile, explicitly enabled with a **loopback-only** signed HTTP fixture, can create a `verified_commerce` order and immutable payment attempt in one transaction. The attempt fixes payer OpenID, AppID, merchant, merchant order number, amount, currency, quote/rule/price versions and expiry. The API requests JSAPI prepay, returns native `wx.requestPayment` parameters and never treats client success as paid. A raw-byte callback or signed original-number query persists a bound payment inbox fact before acknowledgement. The worker locks the order and reservation, rejects synthetic or terminal sources, consumes stock, records `paid` and appends one verified accrual. An unknown cancellation queries and closes the original merchant order before releasing stock. The local attempt close and order cancellation commit in one transaction, so a stale-version retry cannot strand a closed attempt on a pending order. A late paid fact after close remains a visible exception; automatic customer refund for that conflict still needs an approved rule.

An owner can request a test refund against an applied payment. A different approver atomically reserves cash cents and creates one merchant refund number and line allocation before the worker calls the channel. Unknown POST results query that same number. The signed callback or signed query persists a refund inbox; only channel `SUCCESS` applies cumulative integer-cent commission reversal. Multiple partial refunds, replay, closed/abnormal statuses and cumulative overdraw are isolated tests. Unsupported vouchers, freight or points allocation are rejected. Both payment and refund inboxes have due-time ordering, bounded attempts, quarantine and authorized audited redrive. A quarantined outbound refund submission also requires an audited original-number requery; immutable terminal facts cannot be requeued.

In the test profile only, an authorized operator proposes a fulfillment reference and evidence hash. A second operator independently verifies it; the commission beneficiary cannot self-release, and unresolved refund requests block release. A commission beneficiary also cannot approve or reject a referred buyer's refund. This is a **synthetic attestation contract**, not carrier or customer delivery proof. A test member may request a settlement against released net commission; row locks and a per-member advisory lock prevent two requests from reserving the same cents. A different operator approves. Before a first transfer submission, the worker holds affected order locks and rechecks refund exposure and earned balance; a newly invalid reservation is cancelled without a channel call. The transfer worker signs a merchant request, queries the original bill number after an unknown result, and leaves `WAIT_USER_CONFIRM` or `PROCESSING` unpaid. A signed and bound transfer callback is durable before acknowledgement but only a signed original-number `SUCCESS` query appends settlement ledger entries. Callback replay and conflict are tested. An authorized finance page exposes redacted payment/refund/transfer exception summaries, signed recheck and guarded redrive; it cannot edit ledger balances or declare channel success.

The same isolated finance capability can request a WeChat Pay v3 daily `SUCCESS` or `REFUND` trade bill. The adapter signs the bill application, restricts the download URL to the channel host, and checks the application-provided SHA1 against the downloaded bytes. The importer discards raw CSV after validating the required columns, exact CNY cents, identity and original merchant numbers; it stores immutable per-date/type hashes and minimal matching/exception facts. Reimporting the same file returns the original batch; a changed file for the same day/type conflicts. A complete signed daily `SUCCESS` bill is also checked against internally applied paid facts for that Beijing-calendar day, so an internal-only payment becomes an exception even when the file has no provider rows. Refund bill rows record **refund acceptance**, never final refund success; they require a matching internal provider refund ID. This slice does not import fund-flow/transfer bills, detect internal refund acceptances missing from an external bill, or clear an exception after later recheck; those are separate reconciliation requirements before real money.

This is an isolated end-to-end protocol simulation. No real merchant certificates, approved transfer scene, production migration, lawful fulfillment source, tax/settlement policy, complete external bill-file reconciliation, or physical-device money flow have been verified. The complete approved commercial rule registry and real channel enablement remain separate work; `implementedTransactionProfiles` still does not enable MAKE in production. These gaps must stay explicit in owner decisions and release status.

## Deployment sequence and evidence

Forward migrations `202609120002`–`202609120021` were exercised only in isolated local test databases. Production migration, storage permission changes, public UGC, real payment, refund and transfer remain outside this authorization. Before either public gate can open: close the remaining protocol/policy and reconciliation gaps, review merchant/WeChat permissions and applicable terms, obtain named financial/content governance approvals, migrate staging, test callbacks and retries with real platform credentials, run native WeChat Developer Tools and iOS/Android acceptance against the exact source package hash, then request separate production authorization.

## 4. 第三阶段：可量化的服务器访问与交互提速

先按 PRD §13 和 NFR-MEASUREMENT 固化 G0 测量合同：核心动作/API、地域、手机/微信/基础库、网络、冷暖、数据量、负载/到达率、样本、窗口、第三方排除项和高档容量30%余量。签字缺失记依赖，先做探索性测量，不伪造签字或正式SLA。

目标核心API P95≤500ms、核心页面可交互P95≤2s；上传和外部支付单独报告。不要沿用旧800ms写接口门槛。每场景报告 P50/P95/P99、失败/超时、取消/重试、数据规模/包/构建/环境；不能剔除慢失败后声称达标。

实施方案：

- 关联点击反馈、分包、网络排队/DNS/TCP/TLS/首字节/接收、数据处理、setData与可操作；服务端关联HTTP、池排队、SQL/锁、对象存储、事件循环、Worker积压。wx.request profile/wx.getPerformance 不支持的指标标缺失；不跨机相减墙钟、不重复相加嵌套阶段，不采集个人内容或凭据。
- 挂起辅助请求验证核心内容可用；按证据减少重复取数和桥接数据，已读内容保留不闪屏但写动作仍查权威事实。不把缓存价格、权限、积分或护理当写入授权。
- 对照冷暖/正常与≥400ms RTT+5%丢包、完全离线、请求已提交但响应丢失、上传中断、后台恢复、连点、切号。建议每设备×网络×冷暖×旅程100有效动作、核心API每场景1000请求作为候选采样方案，最终依G0合同；少样本不得宣称P95达标。
- 优先顺序：辅助等待/重复请求 → 池/锁/SQL → 图片尺寸/缩略图/私有媒体签名 → 分包与setData → 长列表与键盘滚动 → 微动效。测试低端Android滚动帧耗时、掉帧、峰值内存、单次和累计setData字节/次数、接口次数、包大小。
- 复用现有perf:smoke、perf:capacity、perf:worker-capacity、头像缓存、客服退避、原生分包、COS直传开关/回退。app.inject成绩不能代替真实HTTPS和微信真机。连接复用、HTTP/2、地域、DB索引、CDN分别验证收益与回退，不能盲目改架构。
- 只对明确隔离staging/合成库施压，设停止阈值。SQL EXPLAIN ANALYZE可能执行写入；不要在生产试。所有提速保留鉴权、业务版本、幂等、事务、审核与审计。

## 4. 服务器访问与“丝滑”的验证方案

PRD §13 目标：核心 API P95 ≤500ms、核心页可交互 P95 ≤2s（外部支付/媒体上传另测）。这些不是本轮测得的结果。先完成 G0 测量合同和高档容量 30% 余量口径，不私自把 SLA 写成已承诺。

1. 按一次用户动作关联端与服务：按压反馈 → 分包 → 排队 → DNS/TCP/TLS → 首字节/接收 → 数据处理 → setData 回调 → 关键操作可用；服务端对应接入、池排队、SQL/锁、对象存储、Worker lag。同一 correlation ID 脱敏串联，不采集 token/OpenID/聊天正文/地址，不相加重叠时间或跨机墙钟相减。
2. 先测四个主 Tab、选品到订单、上传、客服首屏/连续消息。微信真机同时记录首屏、最大单次/累计 setData 字节与次数、请求次数、图像大小、滚动帧耗时/掉帧/内存；API 的 app.inject 成绩不含公网 TLS、微信桥或真机渲染。
3. 冷/暖、弱网≥400ms RTT+5%丢包、离线、响应丢失、后台恢复、快速切页/账号分别对照。建议每设备×网络×冷热×旅程100有效样本、API每场景1000次为起步方案，最终依签字合同；少样本仅探索。超时和失败计入分母，报告 P50/P95/P99 与失败率，禁止只算成功快请求。
4. 按证据排序：去掉辅助等待/重复请求；池/锁/SQL问题；缩略图/媒体签名与缓存；小包与少量 setData；列表分页/滚动；最后微动效。复用既有头像缓存、客服差量退避、分包和上传回退，禁止未经验证恢复所有 GET 缓存或缓存权威资金事实。
5. API 当前已锁 Fastify5.12.3/pg8.23.0；保留 PR4 真实 SQL 取消、释放一次、统一期限、未知提交结果等修复。不要因本地P95小幅变化去删事务/权限。HTTP/2、直连与 Cloud HTTP、部署地域/连接复用、CDN、DB索引分别比较，确认收益后才改；Cloud HTTP 逻辑取消不宣称物理中断。

## 6. 商业闭环的分阶段交付

- **A 源码与可用性**：从最新 main 定位，不重复应用 PR4 patch；先复现 PERF-11/12 和逐页问题，再小批修复、回归。当前确认的 UI-01 已关闭。
- **B 原生体验**：沿用已恢复的唯一项目开发者工具入口，完成代表旅程与当前包全状态矩阵；样式逐页按证据调整，完成后阶段性 UX 审计。按压/导航反馈与服务端真实结果分开。
- **C 正式交易闭环**：商品资质/库存→报价→订单→真实支付核验→履约/签收→PLANNED护理→显式激活→记录→售后/退款→佣金/资格修正。关闭的业务不要展示可用按钮；已发生订单即使关门仍须可查询、售后、对账。
- **D 运营、安全、平台**：对象级权限、私有文件、UGC内容安全/人工队列/投诉时限、合法协议与数据权利执行、客服值班和不良反应升级、库存与账单异常、密钥证书轮换、备份恢复/回滚、成本告警和独立 staging。没有选入当前发布组的购物车、复杂成长、AI经营、多渠道连接器不临时扩进来。
- **E 发布与反馈**：不可变 release manifest 绑定代码/包/配置/迁移/域名/发布组/证据；体验版双平台验证后平台审核，再按已批准范围灰度。定义回退条件和负责人；上线后观察关键旅程失败、支付差异、Worker积压、客服响应和用户投诉，而不只看PV。月可用性不足观测窗口时仍标缺证。

每段都要交代码、可重复验证、缺陷状态、回滚、GitHub PR/Actions，不以增加报告代替施工。需要负责人提供的只有真实账号/环境/政策证据和最终不可逆发布决策，日常实现与可逆修复持续推进。[下一轮完整提示词](CHATGPT-GITHUB-NEXT-PROMPT.md)已按这些阶段重写。
